# Промпт для архитектора: условия подготовки AC пагинации SERP

Рассматриваем изменение `d54ee5b..9bc5f65`: проектируемый API
`loadSerpPages(inputUrl, options)`. Рабочее дерево на момент анализа было чистым.
Сейчас `loadSerp` и CLI загружают одну страницу; новый API должен собирать всю
выдачу, сохраняя их существующие контракты. Оба новых API — `loadSerpPages` и
`save-html.renderPages` — пока не реализованы.

Подготовка зависимых критериев в `acceptanceCriteria.md` остановлена по
ACR-09, ACR-18 и ACR-19. Контракт прямо оставляет открытым B1: реальная
двухстраничная, одностраничная без навигации и пустая выдачи не получены.
Историческая попытка закончилась HTTP 429/CAPTCHA и не подтверждает пагинацию.
Этот файл содержит вопросы и требуемые уточнения, а не критерии приёмки.

## 1. Подтверждение готовности и конца выдачи

**Источники:** [LOAD_SERP_PAGES.md](docs/LOAD_SERP_PAGES.md), строки 102–173,
355–377, 598–609, 717–753;
[PAGINATION_FIXTURE_PROTOCOL.md](docs/PAGINATION_FIXTURE_PROTOCOL.md),
строки 3–8 и 25–67;
[SEQ-2.mmd](docs/SEQ-2.mmd), комментарии B1 и ветка ожидания готовности.

**Недостающая информация:** конкретные подтверждённые признаки завершённой
пагинации и языконезависимого конца для выдачи с результатами без навигации
и для пустой выдачи на целевом `hl`. Нет переходных снимков, позволяющих
отличить конец от состояния, в котором результаты появились раньше навигации.

**Решение приёмки, которое нельзя зафиксировать как подтверждённое:** при каких
реальных состояниях Google вызов должен успешно вернуть полный результат или
`[]`, а при каких — продолжить ожидание и вернуть `load/browser-timeout`.
Отсутствие навигации, стабильный DOM и существующий текстовый признак en/ar
не подтверждают успешное завершение согласно самому контракту.

**Требуемое уточнение:** выполнить наблюдения трёх обязательных сценариев по
протоколу B1; сохранить очищенные конечные и переходные HTML, URL, статусы,
фактический href next и результаты. Зафиксировать подтверждённые условия
готовности и конца в контракте и согласовать с диаграммами. Если наблюдений
недостаточно, оставить зависимую успешную поддержку открытой; описанный fallback
не считать закрытием B1 и не подменять наблюдения синтетическими фикстурами.

**Классификация:** вызвано новой функциональностью. Для существующей загрузки
одной страницы подтверждение полноты всей выдачи не требуется.

**Зависимый охват:** успешный полный обход, одностраничная и пустая выдачи,
завершение ожидания при задержанной навигации; исходные UT AC-06, AC-07, AC-09
и относящиеся к готовности части AC-12.

## 2. Совместимость защищённой идентичности с реальными переходами

**Источники:** [LOAD_SERP_PAGES.md](docs/LOAD_SERP_PAGES.md), строки 48–66,
253–336, 573–594, 717–746;
[PAGINATION_FIXTURE_PROTOCOL.md](docs/PAGINATION_FIXTURE_PROTOCOL.md),
строки 27–50, 68–108;
[Cls-0.mmd](docs/architecture/Cls-0.mmd), комментарии Open B1.

**Недостающая информация:** доступная реальная цепочка
«вход → конечный URL первой страницы → href next → конечный URL второй страницы»,
подтверждающая сохранение защищённых параметров, включая `q/hl/gl`, рост `start`
и допустимые изменения служебных параметров. Контракт называет политику
консервативным предложением, которое ещё подлежит подтверждению B1.

**Решение приёмки, которое нельзя зафиксировать как подтверждённое:** какие
входы обеспечивают полный обход реальной выдачи при выбранной политике,
а какие реальные переходы должны прекращать его с `pagination`. Одни
синтетические проверки отклонения изменённого URL не доказывают совместимость.

**Требуемое уточнение:** получить базовую серию с неанглийским `hl` и заданным
`gl`; записать перенос параметров и фактическую следующую ссылку. Отдельно
наблюдать URL из адресной строки и формы поиска, как требует протокол.
Сопоставить наблюдения с контрактом и явно согласовать необходимые изменения
входного/служебного списка или политики. Не исправлять URL автоматически
и не объявлять неподтверждённые исключения допустимыми.

Реестр `num/tbm/tbs/lr` сейчас пуст. Их явное указание однозначно отклоняется
на `input`; это правило не является пробелом. Положительная поддержка любой
записи потребует отдельной двухстраничной серии и нормативной записи точных
значений либо границ семейства и сочетаний по строкам 292–319 контракта и
81–108 протокола. Не объявлять поддержку всего параметра по одному примеру.

**Классификация:** вызвано новой функциональностью. Правила переходов между
страницами и новый закрытый входной список не нужны существующему CLI.

**Зависимый охват:** успешный переход между страницами и подтверждённая
совместимость поисковой идентичности; исходные UT AC-02, AC-04, положительные
сценарии AC-05 и AC-13. Положительные сценарии допуска значений из реестра
не входят в подтверждённый текущий охват AC-01.

## Сопутствующая проблема источников

В строке 10 [LOAD_SERP_PAGES.md](docs/LOAD_SERP_PAGES.md) и источнике S8
[Cls-0.mmd](docs/architecture/Cls-0.mmd) указан `docs/ARCHITECTURE_REVIEW.md`,
но файла нет в коммите `9bc5f65` и рабочем дереве. Восстановить доступный источник
решений либо исправить ссылки. Классификация: вызвано новой функциональностью,
поскольку ссылки появились в её документации. Само отсутствие файла не
доказывает поведенческое противоречие и не выделяется как отдельный блокер AC.

## Ожидаемый результат работы архитектора

Зафиксировать результаты B1 и принятые изменения контракта/диаграмм со ссылками
на очищенные артефакты. Для оставшихся открытых вопросов явно указать
затронутые успешные сценарии; не помечать их подтверждёнными. Отсутствие будущей
реализации `renderPages` само по себе не требует изменения требований и не
считается дополнительным пробелом при формулировании AC.

После разрешения существенных вопросов подготовить `acceptanceCriteria.md`
по внешним наблюдаемым обязательствам нового API и сохранению затронутых
контрактов. Сохранить существующие идентификаторы AC-01…AC-17; при разделении
независимых обязательств добавить новые ID. Внутренние вызовы, классы и
утверждения о выполнении UT не переносить как требования к пользователю API.

Исходная документация и диаграммы при этой подготовке не изменялись.
